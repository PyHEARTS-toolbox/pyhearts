PyHEARTS workflow (beginner-friendly)

PyHEARTS turns raw ECG into an interpretable, beat-by-beat feature table by detecting beats, fitting physiologically constrained P/Q/R/S/T wave models, and extracting morphology + interval features (plus optional recording-level summaries like HRV).

Step details (click a flowchart box to toggle)

2 Raw ECG signal
  • Input: a 1D ECG array (mV) and sampling_rate (Hz).
  • Output: ECG signal ready for preprocessing and beat detection.
  • Tip: if you have both raw and filtered signals, PyHEARTS can use the raw signal for polarity detection (helps when filtering flips/inverts appearance).
  • Goal: produce a beat-by-beat, interpretable feature table (not a black-box score).
1 Config / presets
  • Choose physiology: species preset (human vs mouse) sets interval bounds and expected timings.
  • Choose detection tradeoff: sensitivity controls recall vs precision (more sensitive can include more noisy detections).
  • Input: analysis intent (species), tolerance for missed beats vs false positives (sensitivity), and any overrides.
  • Output: a complete configuration used by preprocessing, detection, validation, and fitting.
  • Advanced: ProcessCycleConfig exposes thresholds, search windows, validation bounds, and detector selection.
3 Preprocess (filtering & detrending)
  • Input: raw ECG time series.
  • What it does: reduces baseline wander + high-frequency noise so peaks and boundaries are easier to find.
  • Typical steps: bandpass, optional notch (50/60Hz), optional polynomial detrending.
  • Output: cleaned ECG series used for downstream detection and fitting.
4 Signal quality check (QC)
  • Input: preprocessed ECG.
  • What it does: assesses quality indicators (e.g., SNR, baseline wander, amplitude/artifact).
  • How to use it: treat QC as “context” for interpreting results; low QC usually means more NaNs / lower fit quality.
  • Output: QC metrics/flags (typically warnings rather than a hard stop).
5 R-peak detection
  • Input: preprocessed ECG (and optionally raw ECG for polarity detection).
  • Goal: find each heartbeat (R-peak indices). This is the backbone for segmentation and RR-based metrics.
  • Robustness: refractory period + physiologic BPM bounds reduce double-counting and noise peaks.
  • Polarity: handles upright vs inverted R-peaks (so later steps can assume consistent orientation).
  • Output: R-peak sample indices (beat timestamps).
6 Epoch into cycles
  • Input: ECG + R-peak indices.
  • What it does: cuts the ECG into beat-centered windows (one “cycle” per beat) using RR timing.
  • Optional filtering: template correlation / variance rules can remove outlier beats (motion artifact, ectopics, etc.).
  • Output: an epochs table/dataframe (cycle segments) used to process each beat independently.
7 Per-cycle processing loop
  • Input: epochs (cycle segments) + configuration.
  • What it does: iterates over cycles, running detection + fitting + feature extraction per beat.
  • Why: beat-level outputs preserve variability that gets lost in recording-level averages.
  • Stability: can reuse previous beat’s parameters as seeds to improve fitting convergence.
  • Output: per-cycle intermediate results populated into the output table (best-effort; failures become NaN for that beat).
8 Fiducials: P/Q/R/S/T + boundaries
  • Input: one cycle segment (beat window) + config search windows/thresholds.
  • What it does: detects wave peaks (P,Q,R,S,T) and boundaries (onsets/offsets) needed for intervals.
  • How: timing windows + derivative/wavelet-based cues + SNR gating to reduce false positives.
  • Output: candidate fiducials (peak indices + boundaries) used for validation + constrained fitting.
9 Physiology validation
  • Input: detected fiducials/boundaries for the beat.
  • Temporal order: enforces plausible ordering (P→Q→R→S→T) when waves are present.
  • Interval bounds: checks PR/QRS/QT/ST/RR ranges (species-specific).
  • Behavior: when detection is uncertain, PyHEARTS can store NaNs rather than forcing a bad measurement.
  • Output: validated (or rejected) fiducials and intervals for the beat.
10 Constrained Gaussian fitting
  • Input: cycle segment + validated fiducials (initial guesses/bounds).
  • What it does: fits Gaussian (or skewed Gaussian) models for each wave under bounded, physiologic constraints.
  • Why: provides consistent, interpretable parameters (center/height/width) and robust boundaries.
  • Output: per-wave fit parameters + reconstructed waveform (used for fit metrics).
11 Per-beat feature extraction (~185 columns/beat)
  • Input: per-wave fit parameters + validated boundaries + the beat signal.
  • Shape (per wave): 5 waves × 33 metrics = 165 (timing, widths, amplitudes, slopes, area, symmetry, sharpness, indices).
  • Intervals/ST: 14 interval/ST metrics (PR/QRS/QT/RR/PP, QTc variants, ST elevation/slope/deviation, etc.).
  • Extras: 3 pairwise amplitude diffs + fit metrics (R²/RMSE) + cycle_trend.
  • Missing waves: supported; unavailable values are stored as NaN (so you can filter/impute downstream).
  • Output: one row of features for this beat.
12 Aggregate beat-level feature table
  • Input: per-beat feature rows from the processing loop.
  • Output: a DataFrame with one row per beat and ~185 columns.
  • Use cases: interpretable ML, beat-to-beat analysis, arrhythmia burden summaries, phenotype discovery.
13 Beat-to-beat variability summary (default 65 metrics)
  • Input: beat-level feature table.
  • What it does: summarizes variability across the recording for a small “priority set” of features.
  • Default count: 13 priority features × 5 stats (std/cv/iqr/mad/range) = 65 metrics.
  • Customizable: you can change the priority feature list to target your phenotype (e.g., QT variability, amplitude variability).
  • Output: a recording-level dictionary/table of variability metrics.
14 HRV metrics (7 metrics)
  • Metrics: average HR, SDNN, RMSSD, NN50, pNN50, SD1, SD2.
  • Input: RR intervals derived from R-peaks in the feature table.
  • Note: needs enough beats for stable estimates (very short recordings won’t be reliable).
  • Output: a recording-level dictionary/table of HRV metrics.
15 Outputs (files + metadata)
  • Input: beat-level feature table + optional summaries (variability/HRV).
  • Main: {file_id}_pyhearts.csv (beat-level feature table).
  • Reproducibility: {file_id}_meta.json (config + environment + version info).
  • Optional: HRV metrics CSV, RR intervals CSV, variability metrics CSV, plots.
  • Output: files on disk for analysis, sharing, and reproducibility.
16 Plots (optional)
  • Input: per-beat detections/fits/features.
  • Purpose: sanity-check detections, boundaries, fits, and rejected cycles.
  • Best for: debugging datasets, tuning sensitivity/presets, explaining results to non-technical audiences.
  • Output: figures that visualize cycles, fiducials, and fit quality.
